# base 16-32-64 ( 2026/09/02 )
## Description
base16、base32、base64 を組み合わせた新しいエンコーディング方式を考えました。
## Solve
配布されるコードは以下の通りです。
``` py
import os
import random
from base64 import b16encode, b32encode, b64encode

flag = os.environ.get("FLAG", "Alpaca{**** REDACTED ****}").encode()

for i in range(20):
    base = random.choice([16, 32, 64])
    if base == 16:
        flag = b16encode(flag)
    elif base == 32:
        flag = b32encode(flag)
    elif base == 64:
        flag = b64encode(flag)

flag = flag.decode()

print(flag)
```
20回flagをbase16,32,64のいずれかでエンコードしたものがoutput.txtに残っていることがわかります。
ここで、base16,32,64のそれぞれのパディングについて考えてみます。
| base | padding数 |
| --- | --- |
| 16 | 0 |
| 32 | 0,1,3,4,6 |
| 64 | 0,1,2 |

このように、何でデコードするかによって、パディング数が変化するため、ある程度どのエンコード形式か、というのが判定できます。
ここでおそらく疑問点となるのが、base16,32,64のすべてで、正しいと判断できるパディング数が存在する点です。(0など)
ここで、仮にbase64エンコードされたデータ長が16であり、64種の文字が均一な分布をしているとすると、これらの文字がすべてbase32で使われている文字でもある確率は、32 / 64 = 1/2から、(1/2)<sup>16 * 100 = 0.15[%]より、0.15%となるため、無視できるほど小さいことがわかります。また、この値はデータ長が長ければ長いほど小さくなります。
よって、base16,32,64のいずれとも読めてしまう場合をほとんど考慮ず、順に16,32,64でのデコードを試す、といった作業を20回繰り返せばよいことがわかります。

## Solver
```py
import os
import random
from base64 import b16decode, b32decode, b64decode

with open("/home/kali/Desktop/DailyAlpacaHack/base-16-32-64/output.txt", "rb") as f:
    c = f.read().strip()

for i in range(20):
    try:
        c = b16decode(c)
        continue
    except Exception:
        pass
    try:
        c = b32decode(c)
        continue
    except Exception:
        pass
    try:
        c = b64decode(c)
    except Exception:
        print(f"Error in {i}")

print(c)
```
